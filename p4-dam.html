From design to production code in P4 DAM

P4 DAM is Perforce’s digital asset management product, helping teams organise and review digital assets. When its front-end team fell from six developers to two, I began taking some features from design through to production code.

The problem

P4 DAM’s 3D viewer lets people inspect models and materials. Improvements depended on a front-end team that had fallen from six developers to two.

My usual process was to design a feature in Figma and hand it over for implementation. That left the remaining developers responsible for building the interface and resolving any gaps in the designs or requirements.

Role and team

I designed and implemented front-end features using Claude Code, reviewing and correcting its output before submitting the code to developers for review and integration.

For features handed over to developers, I created Claude skills that turned feature discussions into written specifications and visual handovers.

My product owner set priorities and reviewed delivery. He also built an AI system that provided feedback from the code repository, which helped me clarify requirements and prepare the handovers.

Key decisions

Make the viewer more useful for asset inspection.

The existing viewer showed assets against a grey or single-colour background, while competing viewers offered richer lighting environments. Settings were accessed through a corner icon.

I designed and implemented selectable image-based lighting environments and moved the settings into a persistent, movable and resizable panel. Reviewers could adjust the lighting while inspecting the model.

Keep environment selection beside the asset.

I chose miniature environment previews within a compact sidebar selector. A separate gallery would have offered larger previews, but it would also have taken attention away from the asset. I wanted reviewers to see the lighting choice and its effect together.

Give developers a clearer picture of each feature.

Implementing features addressed part of the capacity problem. For work still going to developers, I focused on making the handovers more complete.

I created a Claude skill to produce specifications and visual snapshot documents from feature discussions. The snapshots showed interface states alongside the written requirements.

The first version missed states that developers needed, so I revised the skill’s instructions based on their feedback.

Design changes

Improvement Change Benefit
Image-based lighting Added selectable lighting environments to the 3D viewer. Reviewers can inspect shape and materials under different lighting conditions.
Persistent settings Moved settings from a corner icon into a movable, resizable panel. Controls remain available during asset inspection.
Compact environment selector Added miniature environment previews within the settings panel. Reviewers can recognise the lighting environment before selecting it.
More complete handovers Expanded the interface states covered by generated snapshot documents. Developers receive a clearer account of the intended behaviour before implementation.

How I used AI

I used Claude Code to implement the viewer changes, directing the interaction design and checking the generated interface against the product’s existing conventions.

For the lighting selector, Claude initially produced a modal gallery. I redirected it towards miniature previews in the settings panel so reviewers could choose an environment while keeping the model in view.

I also corrected generated styling to use the product’s established utility classes.

What I would have done differently

I would have involved developers earlier in creating the specification and snapshot templates.

I initially made assumptions about the detail they would need. Reviewing one early handover together would have exposed the missing states before I reused the format across features.
