From design to production code in P4 DAM

Context
P4 DAM helps teams organise and review digital assets. When our front-end team dropped from six developers to two, I began taking features from design through to production code. Working with Claude Code and sharing files through GitHub allowed me to take on implementation work and give developers handovers they could use directly.

Role and team
I designed and implemented front-end features and developed tools for developer handovers. My product owner set priorities and reviewed delivery. Developers reviewed my code and integrated it into the product.

The problem

Front-end developers had been reassigned, leaving us with a much smaller team. Customer demands were still growing, and competitors were using AI to release features faster and develop their products.

We needed to keep delivering with fewer developers. That meant I also needed to change how I worked as a designer and take on more of the work involved in getting a feature into production.

How I changed the way I worked

Build features in the product’s code.

I began using Claude Code to implement selected features directly in the product. I directed the design, checked the generated interface and corrected the code before sharing it through GitHub for developer review.

This gave developers a working interface they could inspect and use. I could hand over files more quickly than through Figma alone, and they had less of the interface left to build from scratch.

Give the work context before building it.

My product owner and I built an AI system that took feedback from the existing repository and directly from users, then turned it into Markdown files.

I used those files as context for my AI workflows. They helped me clarify requirements and bring the relevant product information into the work before designing and building a feature.

Make behaviour clear in the handover.

For features going to developers, I created Claude skills that produced specifications and visual snapshot files. I used these alongside working prototypes and CLAUDE.md context to explain the interface states and intended behaviour.

Developers could try the prototype and inspect its code instead of relying on Figma screens and asking me to explain each interaction. The snapshots gave them a record of the states they needed to account for.

The first version of the snapshot skill missed some of those states. I revised its instructions using developer feedback. The handover below covers six lighting and background states from the viewer feature.

Example feature: the 3D viewer

The viewer is one example of the work I designed and built with Claude Code. It lets people inspect 3D models and materials inside P4 DAM.

The feature involved selectable HDRI lighting environments and controls that reviewers needed to use while inspecting an asset. I had to consider how the controls behaved, how the lighting affected the model and how to keep both usable in the same view.

Let reviewers inspect assets under different lighting.

The existing viewer showed assets against a grey or single-colour background. Competing viewers offered richer lighting environments, allowing reviewers to see how shape and materials looked under different conditions.

I designed and implemented selectable HDRI environments so reviewers could change the lighting around a model without leaving the product.

I also moved the settings from a corner icon into a panel that could stay open. Reviewers could move or resize it while working with the model, keeping the controls available during inspection.

Keep the lighting choices beside the model.

Claude initially created a modal gallery for choosing an environment. That offered room for larger previews, but it took attention away from the model reviewers were inspecting.

I changed the design to use small previews inside the settings panel. Reviewers could choose an environment and see its effect while keeping the asset in view.

Check the generated code against the product.

I also reviewed the styling Claude produced. In the comparison below, it had used individual pixel values and custom colours.

I replaced them with the product’s established Tailwind CSS and adjusted the spacing, corner radius and colours to fit the existing interface. This was part of reviewing the feature before passing it to developers for integration.

Results

  • My work in production code and faster handovers helped the team ship around 25% more features in Q3 2026 than in Q2. I was contributing implementation capacity at a time when the front-end team had fewer developers.
  • Planning meetings fell from about an hour to around 30 minutes per feature, by my estimate. Developers had fewer interactions to clarify with me and reported that the revised handovers made features significantly easier to work through.
  • My system won Best Designed at Perforce’s 2026 company-wide AI hackathon. At least three product teams now use the skill or parts of its workflow.

What I would do differently

I would have liked to involve developers earlier in creating the specification and snapshot templates. Production demands and pressure to release features meant I didn’t get that opportunity at the start.

I initially made assumptions about the detail they would need. Reviewing one early handover together would have exposed the missing states before I reused the format across features.
